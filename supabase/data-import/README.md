# One-time Base44 → Supabase data import

This folder holds a **one-time data load**, not a schema migration — nothing
here touches table structure (that's what `supabase/migrations/` is for).
`2026-09-27_base44_export_import.sql` loads a real production data export
from Base44 (15 CSVs, one per entity, taken from the Base44 admin panel) into
this project's current Supabase schema, generated by `build_import_sql.py`
from those CSVs.

## Before running it

1. Apply every migration through `supabase/migrations/0015_task_completions_direct_type.sql`
   first. The export contains `task_completions` rows with
   `task_type = 'direct'`, which the original schema's CHECK constraint
   (`0001_init.sql`) never actually allowed — 0015 fixes that pre-existing
   bug. The import script itself checks for this and aborts with a clear
   error if 0015 hasn't been applied yet, rather than failing confusingly.
2. Make sure `6292bb9d-89e3-4054-a822-38960eeafa16` exists in `auth.users`.
   Every imported row's `created_by_id` is set to this one account (Base44's
   own `created_by_id` values are its internal user ids, which don't
   correspond to any Supabase auth account, and `created_by_id` is a real
   foreign key to `auth.users` — this was a deliberate choice, not a
   guess: see the note in `build_import_sql.py`). The script checks this
   too and aborts first if it's missing.
3. **Read the warning block at the top of the generated SQL file before
   running it.** This import *replaces* the current contents of 15 tables
   (`gaps`, `gap_updates`, `recurring_events`, `recurring_overrides`,
   `task_completions`, `direct_tasks`, `events`, `daily_summaries`,
   `daily_routines`, `warehouse_items`, `withdrawal_requests`,
   `equipment_holdings`, `equipment_settings`, `constraints`,
   `access_requests`) — an explicit choice, made because this export is
   meant to become Supabase's real data rather than merge with whatever
   sample/test rows are there now. In particular, deleting `events` cascades
   to any `event_contacts` / `event_confirmations` rows tied to an event
   being deleted (a feature Base44 never had, so this export can't restore
   them) — back those up first if real ones already exist.
4. Run it once, in the Supabase SQL editor (or `psql`), the same way this
   project already runs `supabase/migrations/*.sql` and
   `supabase/test-data/seed_test_playground.sql` by hand. It's wrapped in a
   transaction, so a failure partway through rolls back everything.

## Data-quality fixes applied during the conversion (not just a straight copy)

- **`access_requests.assigned_role`**: an earlier version of this script
  "corrected" this value from a plain `פ` (U+05E4) to the final-form `ף`
  (U+05E3), reasoning from `0001_init.sql`'s CHECK constraint text (written
  with `ף`). That was backwards — running the import against the real
  Supabase project rejected the "corrected" `ף` value outright
  (`access_requests_assigned_role_check` violation), while the app's own
  source overwhelmingly reads/writes this role with the plain `פ` this
  export already uses (`src/components/AdminPanel.jsx`, `TopNav.jsx`,
  `AppLayout.jsx`, `WarehouseItemForm.jsx`, `Klaf.jsx`, `Equipment.jsx`,
  `src/testdata/fixtures.js` — only two files in the whole app use `ף`). The
  migration file's own literal is evidently out of sync with what's actually
  deployed; fixing that is a schema question for `supabase/migrations/`, not
  a data-import one, so it's left alone here — this script now passes the
  export's original `פ` value through unchanged.
- **ids**: Base44's own row ids (Mongo-style ObjectIds, e.g.
  `6aa1c4cc72f2848a151a92c0`) aren't valid Postgres `uuid` values, so every
  row gets a freshly generated one — deterministically, via
  `uuid5(NAMESPACE, "<table>:<original id>")`, so re-running the generator
  against the same (or a newer, overlapping) export reproduces the same
  ids. This is what keeps `gap_updates.gap_id` pointing at the right
  (regenerated) `gaps.id`, `recurring_overrides.recurring_event_id` at the
  right `recurring_events.id`, and `task_completions.task_id` at the right
  `events.id` / `direct_tasks.id` / `daily_routines.id` depending on
  `task_type` — none of these are a plain copy of the original text ids.
- **One `gap_updates` row was dropped**: it referenced a `gap_id` that
  doesn't exist anywhere in the Gap export (that gap was presumably deleted
  in Base44 after this status-change log entry was written, and the two
  collections were exported independently rather than as one consistent
  snapshot). `gap_updates.gap_id` is a real foreign key, so this row can
  never be inserted — it's dropped rather than pointed at a fabricated
  placeholder gap. The generator prints a note for any row it has to drop
  this way (checked for `gap_updates` and `recurring_overrides`, the only
  two tables in this export with a real foreign key to another table in it).
- **`daily_summaries.entries`**: normalized every entry from the old
  `{area, notes}` shape to the current `{areas: [...], pluga, notes}` shape
  (see `entryAreas()` in `src/pages/DailySummary.jsx` /
  `src/components/klaf/KlafSummary.jsx`) rather than leaning on that
  back-compat reader forever.
- Everything else (empty strings on a required field, a missing JSON array
  defaulting to `[]`/`{}`, etc.) is handled the same way — see the comments
  in `build_import_sql.py`, one function per table.

## Re-running against a newer export

Drop a fresh set of the same 15 CSVs into a folder and run:

```
python3 build_import_sql.py <csv_dir> <output.sql>
```

Matching is by filename substring (`-Gap_export`, `-GapUpdate_export`, ...),
so Base44's own `<hash>-<Entity>_export_1.csv` naming works unchanged.
